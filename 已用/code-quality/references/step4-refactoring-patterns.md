# 步骤 4：重构模式与技术选型（细则）

针对步骤 2-3 的问题匹配经典重构手法，输出模式匹配表与分步操作计划。

**何时重构**：加新功能前（先让改动容易）、测试通过后（red-green-refactor）、见到坏味道时、评审反馈时。
**何时不重构**：无测试覆盖、紧 deadline 且无安全网、即将被替换的代码、还没读懂它做什么。

**坏味道 → 手法对照**

| 坏味道 | 重构手法 |
|--------|----------|
| 过长函数 | Extract Method（按"做一件事"切块并命名） |
| 深层嵌套箭头代码 | 卫语句提前返回（guard clauses） |
| 原始类型偏执 | 值对象封装校验（Email/Phone/Money） |
| 特性依恋 | Move Method 到数据所在处 |
| 按类型 switch | Replace Conditional with Polymorphism |
| 长参数列表 | Introduce Parameter Object |
| 魔法数字 | 提取命名常量 |

**遗留代码策略**：Strangler Fig（绞杀者，新旧并行逐步替换）、Branch by Abstraction（抽象分支，接口隔离后换实现）。
**渐进路径**：每步可独立验证；评估回归风险与所需测试；按优先级生成操作清单。

**安全流程**：1 确保测试存在（没有先补）→ 2 每次只做一个小改动 → 3 每步后跑测试 → 4 频繁提交便于回滚 → 5 审查 diff 确认行为未变。

**检查表**：[ ] 开始前测试通过 [ ] 每步小而聚焦 [ ] 每步后测试通过 [ ] 只改结构不改行为 [ ] 可读性提升 [ ] 提交信息说明重构目的。

# 步骤 3：整洁代码与 SOLID 原则评审（细则）

按 Uncle Bob 原则逐项评审，输出 SOLID 合规报告与原则性重构方向。

**核心原则**
- 童子军规则：让代码比你发现时更干净
- 命名揭示意图；需要注释解释的名字就是错名字。类=名词短语，函数=动词短语，布尔=疑问句（`isActive`/`hasPermission`）
- 函数：短小，只做**一件事**；理想 0-2 参数（3+ 是坏味道）；无副作用；命令-查询分离；DRY 但三次重复再抽象；能提取就提取
- 注释：好代码自文档化；删除注释掉的代码；禁止复述代码的注释
- 错误处理：异常/Result 优于错误码；不返回 null、不传递 null；try-catch 置顶；错误处理本身就是"一件事"
- 对象 vs 数据结构：对象隐藏数据暴露行为，数据结构反之，不要混血；迪米特法则（禁止 `a.getB().getC().doThing()`）

**SOLID 速查（附启发式判断）**
- S 单一职责：一个类只有一个变更理由/服务一个角色。描述类时用了"和"→ 多职责
- O 开闭：扩展靠新代码而非改旧代码。加功能要改 switch/if-else 链 → 违反 OCP
- L 里氏替换：子类可无 surprises 替换父类。子类覆写行为令调用方意外 → 违反 LSP
- I 接口隔离：接口要窄。实现时被迫写空方法或抛 not-supported → 接口太肥
- D 依赖倒置：依赖抽象不依赖具体。类自己 `new` 依赖 → 违反 DIP，改构造注入

**Clean Architecture 依赖规则**：源码依赖只能指向内层（Entities ← Use Cases ← Interface Adapters ← Frameworks）；内层不知道外层；跨边界数据用简单 DTO/值对象，绝不传框架类型；数据库/Web/框架都是可替换细节；所有具体装配只发生在最外层组合根。小项目可先两层（domain + infrastructure），依赖规则不可谈判，其余视复杂度缩放。

**坏味道红旗**：僵化（小改动连锁改）、脆弱（一处改坏无关处）、不可移动（复用需拖依赖）、无谓复杂（投机泛化）、无谓重复、不透明；长函数、大类、长参数表、布尔标志位、按类型 switch。

**TDD**：三定律（先写失败测试→只写刚好失败的测试→只写刚好通过的代码）；FIRST（Fast/Independent/Repeatable/Self-validating/Timely）；测边界与行为，不测实现。

> **边界**：此处仅保留与代码评审相关的一行速查。测试体系方法论（TDD 工作流、测试生成、E2E/API、QA 计划）统一维护在 **tech-test-automation** skill，涉及测试专项任务请转过去。

**评审顺序**：1 可读性（30 秒能懂？）→ 2 命名 → 3 函数可提取性 → 4 单一职责 → 5 依赖方向 → 6 耦合 → 7 错误处理 → 8 测试。

# Test Fixing — 失败测试诊断-修复循环

> 源自 engineering-workflow/test-fixing。定位：修复**既有失败测试**的诊断-修复循环（先跑、分组、逐组最小修复、验证）。从零编写测试/制定测试策略走 skillsets 六步主线。

## 触发场景

- "fix these tests / make tests pass / 测试挂了，修一下"
- 重构或实现完成后测试套件变红
- CI/CD 因测试失败而中断

## 诊断-修复循环

### 1. 初次运行，摸清全貌

```bash
make test        # 或项目等价命令：pytest / npm test / go test ./...
```

从输出中提取：失败总数、错误类型与模式、受影响的模块/文件。

### 2. 智能错误分组

按三个维度归组：
- **错误类型**：ImportError / AttributeError / AssertionError / TypeError…
- **模块/文件**：同一文件引发多处失败 → 合并为一组
- **根因**：缺依赖、API 变更、重构影响、环境配置

分组优先级：**受影响测试数多的组先修**；同数量时**按依赖顺序**（基础设施先于业务功能）。

### 3. 逐组修复（每组四步）

1. **定位根因**：读相关代码；用 `git diff` / `git log -p` 查最近改动；归纳错误模式
2. **最小修复**：只改导致该组失败的最小范围，遵循项目约定，不顺手重构
3. **子集验证**：只跑该组相关测试确认转绿：
   ```bash
   uv run pytest tests/path/to/test_file.py -v
   uv run pytest -k "pattern" -v
   ```
4. **当前组全绿前不进入下一组**

### 4. 修复顺序策略

**基础设施类**（ImportError、缺依赖、配置问题）
→ **API 变更类**（函数签名变化、模块重组、重命名）
→ **逻辑类**（断言失败、业务 bug、边界处理）

### 5. 最终验证

- 跑完整套件：`make test`
- 确认无回归、覆盖率未因修复而受损

## 最佳实践

- 一次只修一组，每修一处立即跑聚焦测试
- 用 `git diff` 理解失败与最近改动的因果关系
- 在失败输出中找共性模式，避免逐个打地鼠
- 改动保持最小、聚焦——失败测试是信号，不是重写代码的许可

## 示例流程

用户："重构后测试挂了" → `make test` 得 15 个失败 → 分组：8×ImportError（模块改名）、5×AttributeError（签名变化）、2×AssertionError（逻辑 bug）→ 按"基础设施→API→逻辑"顺序逐组修复并子集验证 → 全量套件通过 ✓

# PRD Writer

把一个模糊的产品想法，写成研发能排期、测试能验收、合规能审阅、老板能拍板的 PRD。重点是"可验收"，不是"写得长"。

## 何时使用

- 新功能/新产品立项，需要完整需求文档
- 现有 PRD 缺验收标准、指标口径、异常处理、依赖评估
- 需求评审前需要补齐评审表与决策记录
- 需要做方案对比、MVP 切分、上线与回滚计划

不适用：纯技术设计文档（用架构文档）、纯市场分析（用竞品报告）、纯会议纪要。

## 交付物

1. 一份 15 段结构的 PRD（Markdown）
2. 一张需求追踪矩阵（RTM）
3. 一张多视角评审决策表
4. 一份交付前自检结论

## 15 段骨架

| # | 章节 | 必须回答的问题 |
|---|------|----------------|
| 1 | 文档信息 | 名称、版本、作者、日期、状态、变更记录、评审记录 |
| 2 | 背景与目标 | 为什么现在做；要解决哪 3 个问题；成功指标及口径 |
| 3 | 名词与术语 | 团队内部容易混淆的概念，逐条定义 |
| 4 | 需求范围 | In Scope / Out of Scope，明确本期不做什么 |
| 5 | 方案对比与选型 | 至少 3 个方案；推荐哪个；不选的理由；演进触发条件 |
| 6 | 用户角色与场景 | 角色、目标、典型场景、频率；主流程与外部流程 |
| 7 | 功能需求 | FR-01 起编号；状态词 + 规则 + GWT 验收 |
| 8 | 非功能需求 | 性能、安全、兼容、可访问性、稳定性，全部给数值 |
| 9 | 业务流程与状态 | 状态集合、触发事件、迁移表、禁止回跳 |
| 10 | 数据与埋点 | 核心实体、关键字段、事件、指标口径 |
| 11 | 权限与安全 | 角色 × 功能权限 × 数据权限；密钥与审计 |
| 12 | 异常处理 | 空值、超大、断网、失败、回滚、越权 |
| 13 | 上线计划与依赖 | 依赖三档、MVP 切分、灰度、回滚、上线后验证 |
| 14 | 风险与遗留 | 风险登记册（概率 × 影响）、责任人、遗留问题 |
| 15 | 附录 | 原型线框、用户故事、RTM、合规声明、评审表 |

## 写作硬规则

1. 每条功能需求必须编号（FR-01...），并带 Given/When/Then 验收。
2. 状态词只用：必须（shall）/ 应该（should）/ 可以（may）/ 禁止（must not）。
3. 每个指标必须有：目标值、口径、统计周期、数据来源。估算值必须标注"估算"。
4. 方案对比必须写清"为什么不选另外几个"，不能只夸推荐方案。
5. 依赖必须分三档：阻塞 / 并行 / 可绕过，并给最晚就绪时限与替代方案。
6. 涉及数据采集时，第 11 节必须覆盖数据合规 8 项：分类分级、告知同意、最小化、去标识化、用户权利、留存清理、审计、跨境。
7. 异常处理不能只写 happy path；至少覆盖空包、超大、断网、失败重试、越权、回滚。
8. 成功指标没有 baseline 时，明确写"待建 baseline"，不要编造调研数据。
9. 用户画像基于通用认知时，主动声明"非编造调研数据，上线后校准"。
10. 涉及合规、支付、医疗、未成年人、军事历史题材时，加合规声明并标注需法务确认。

## 需求条目模板

```markdown
### FR-01 功能名称

- 规则：系统必须……；应该……；禁止……
- 边界：输入范围、并发上限、失败策略
- 验收：Given ……，When ……，Then ……
- 优先级：Must / Should / Could
```

优先级用 MoSCoW 汇总，不要每条都写"高"。

## 方案对比写法

| 方案 | 思路 | 成本 | 复杂度 | 体验 | 风险 | 上线速度 | 综合评价 |
|------|------|------|--------|------|------|----------|----------|

结论必须包含：

- 推荐方案与 3 条理由
- 不选其他方案的具体原因
- 演进路径与触发条件（例如"安装量达 5000 且运营就绪后启动 v2"）

## 多视角评审

出稿前用四个视角自查，并形成决策表：

| 编号 | 视角 | 发现 | 等级 | 决策 | 修订落点 |
|------|------|------|------|------|----------|
| REV-01 | 产品 | | 高/中/低 | 采纳/部分采纳/拒绝 | 章节号 |
| REV-02 | 研发 | | | | |
| REV-03 | 测试 | | | | |
| REV-04 | 合规 | | | | |

冲突裁决写清原则，例如"覆盖优先、误杀可控"或"安全底线不让步"。拒绝项必须写理由。

## 工作流

1. 澄清：目标用户、核心问题、本期不做什么、成功指标、硬约束（时间/合规/预算）。
2. 选型：列 3 个方案，做对比表，给推荐与演进。
3. 拆需求：按角色旅程拆 FR，每条配 GWT。
4. 补非功能：性能、安全、兼容、异常。
5. 补数据：实体、字段、埋点、口径。
6. 补上线：依赖三档、MVP、灰度、回滚。
7. 自检：跑 references/review-checklist.md。
8. 评审：四视角决策表，逐条闭环。

## 交付前自检

- 15 段齐全
- 每条 FR 有编号 + GWT
- 每个指标有口径 + 周期 + 来源
- 方案对比有推荐 + 不选理由 + 演进触发
- 依赖有阻塞/并行/可绕过分级
- 异常清单覆盖失败与回滚
- 权限模型明确到数据范围
- 合规专项 8 项（如适用）
- RTM 与合规声明已附
- 评审表无未闭环项
